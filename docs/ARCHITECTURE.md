# Architecture

This is a pipeline, not a service. Each stage reads what the one before it produced, writes its own output, and doesn't call back upstream. Nothing here is async or event-driven; a full rebuild is a straight-line pass through the stages below, and the Streamlit app just caches the result and slices it by whatever timestamp the replay clock is set to.

## Components and data flow

```
sim/               generates readings.csv, manual_checks.csv, units.csv, defects.csv, ground_truth.csv
  |
data_access.py     reads the CSVs back in; the only module allowed to touch ground_truth.csv
  |
features/          station_features (per-station, per-bucket aggregates) and unit_features
  |                (per-unit journey). soft_sensors.py fills in partial/manual stations.
  |
detect/            SPC rules + anomaly detection over station_features, one signal per
  |                (station, bucket) where something looked off
  |
predict/           journey_features assembles a unit's full history into one row;
  |                defect_risk.py trains a classifier on it; calibration.py calibrates
  |                the output and decides when to abstain instead of guessing
  |
rootcause/         given a caught defect, traces back through the SPC/anomaly signal
  |                history to a suspected origin station and driver, and lists units
  |                still in flight from that window
  |
actions/           turns a traced alert into a recommendation addressed to an owner role
  |
trust/             logs every prediction to a ledger, resolves it against what actually
                    happened, and runs the ablation backtest

app/                reads the trained pipeline through app/state.py's cached loaders and
                    renders it across six pages. No logic lives in app/ that isn't already
                    in src/twinline/: if a page needs a number, it calls a function that
                    computes it, it doesn't recompute it inline.
```

`schemas/` sits alongside all of this rather than in the flow: it's pydantic models for every config file and every record that crosses a module boundary, so a station config or a prediction record has one typed definition instead of being passed around as loose dicts.

## Point-in-time discipline

Almost every function in `predict/`, `rootcause/`, and the app takes an explicit `as_of_time_s` or `now_s` argument and only uses data with a timestamp at or before it. `journey_features.py` builds a unit's feature row either for its full journey or truncated to a specific checkpoint sequence, depending on whether it's being used for live prediction or for the backtest's mid-journey replay. The Floor Supervisor page's replay clock isn't cosmetic: moving it actually changes which readings, signals, and predictions the page is allowed to see, because every query underneath it is time-gated the same way.

This discipline exists because leakage was the main risk in this project, not an incidental one. We're grading a model against ground truth generated by the same process that produced the training data, on a line where tool wear drifts and a fault's effect compounds the longer it runs. Two things make it easy to accidentally cheat: pulling in ground_truth.csv anywhere in the feature or prediction path (even indirectly, through a derived column that happens to correlate with the defect label), and splitting train/calibration/test randomly instead of chronologically, which would let the model see post-drift behavior during training and get credit for "predicting" something it was shown in a different guise.

We guard against the first with a runtime check in `data_access.py`: it inspects the call stack's `__name__` at the point ground_truth.csv is about to be read, and raises if the caller isn't in `rootcause/` or `trust/` (the two places that are allowed to check answers, because tracing and evaluation are exactly where you're supposed to compare against truth). This is checked at runtime against the actual call stack, not enforced by file layout or code review, so a new module can't quietly start reading it without the guard catching it. We guard against the second by never randomly splitting anything that feeds `predict/`: `time_based_split` in `defect_risk.py` sorts by sequence number first and takes the earliest 60% for training, the next 15% for calibration, and the last ~25% as test, always in that chronological order.

The backtest ablation applies the same discipline to itself: it replays the run using only features knowable at a fixed mid-journey checkpoint (station 16 of 24), not each unit's full journey, so the "would this have caught it in time" question is answered honestly instead of with hindsight.

## Shadow mode

Nothing in this codebase writes to the line. There's no actuator interface, no PLC write, no MES update, not even a stubbed one. The app's alerts, recommendations, and root-cause traces are all advisory text addressed to a named owner role; a human decides what to do with them. The one thing the app does let an operator do is acknowledge or dismiss an alert, and that's logged to the trust ledger for audit, not fed back into the model or used to suppress future alerts on the same station or driver. Each new incident is scored independently from the evidence available at the time. This is a deliberate stance, not a missing feature: a hackathon prototype that can accidentally change what a real line does is a different, much scarier thing to review, and we didn't want to build something that needed that review.

## Onboarding a new plant through config alone

The topology lives entirely in `configs/plant_line_a.yaml`: station IDs, sequence, area, instrumentation tier, which sensors it carries, whether it can cause a defect, whether it's an inspection gate, takt time, shifts, variants. Nothing in `src/twinline/` hardcodes a station ID or a station count; everything downstream (the simulator, the feature store, detection, prediction, the app's line map) iterates `plant.stations` and keys off `sequence` and `instrumentation`. Swapping in a differently-shaped line, more stations, a different mix of rich/partial/manual, different takt, means editing this one file and regenerating data. `configs/model.yaml` holds the simulation and per-module tuning (fault sources, alarm budget, calibration thresholds, cost model); `configs/features.yaml` and `configs/detect.yaml` hold bucketing and rule thresholds that are mostly plant-shape-independent.

The one place this "config alone" claim doesn't fully hold is `configs/soft_sensors.yaml`. Its archetypes name specific donor and blind station IDs (`BODY_FIT` reads `BC-03`, `BC-07`, `BC-09` as donors for `BC-05`, `BC-08`, `FA-08`), because which stations physically share a process family with which others is a fact about the plant, not something we can infer generically from a topology file. A new plant needs its own archetype list written by someone who knows which stations are actually measuring related things. Everything else onboards through config; this one part needs a person who understands the process.
